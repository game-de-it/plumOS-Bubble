## 2. 最優先：`68cbefe` と `89d076d` の実機確認

この2つはまだ実機で見ていない。**3つの変更が同時に入っている**ので、
おかしければどれが原因か切り分けが必要になる。

1. **素子の輝度均一化を既定OFF**（`gg_balance` 0.00）
   → 実機で「RGB素子が全く見えない」の対策。見えるようになったか
2. **階調を締めた**（black 0.28→0.14、gamma 0.90→1.35、bright 2.30→2.60）
   → 「全体的に白っぽい」の対策。黒が締まったか、暗くなりすぎていないか
3. **色を実機に寄せた**（`gg_blueweak` 0.30 新設、ランプを青被り→淡い緑）
   → 青背景が実機のような灰青になったか。赤や橙が失われていないか

### 行き過ぎ／足りない場合の戻し方

| 症状 | 触る |
|---|---|
| 素子が見えない | `Element luma balance` が0か確認。次に `Subpixel strength` を上げる |
| 素子が主張しすぎる | `Subpixel strength` を下げる（0.62→0.45程度） |
| 暗い／眠い | `Black level` 0.14↔0.28、`Panel gamma` 1.35↔0.90、`Brightness` 2.60↔2.30 を連動で |
| 青が残りすぎ／灰色すぎ | `Weak blue filter` 0.30 を上下（0.20で青が残り、0.40でより灰色） |
| 全体の色被り | `Panel cast`。**青被りではなく淡い緑**。実機の白を測った値 |

実機で決めた値は必ず `gamegear-lcd-panel.glsl` の `#pragma parameter` 既定と
`scripts/preview-gamegear-lcd.py` の `P` の**両方**へ反映すること。

## 3. 未決の設計判断：アスペクト比（480x432 か 640x480 か）

**ここが最大の未決事項。** ユーザーの判断待ちで止まっている。

### 事実関係

実機のGame Gearパネルは **4:3の非スクエアピクセル**。
実機写真の画面矩形を測ると 501x376 = 1.33 で確認できる。
160x144を4:3に引き伸ばして表示している。

現在の実装は **480x432（整数3x、10:9）**。実機より**横に20%狭い**。
これはシェーダーの都合であって、幾何としては正しくない。

> 補足：作業中に一度「Game Gearは正方ピクセル(10:9)」と記述したが**これは誤り**。
> 上記のとおり4:3が正しい。過去のコミットログにその誤りが残っている。

### なぜ整数倍が要るのか

パネルパスはセル格子とRGBストライプの位相を**ソースピクセルから**取る。
1ソースピクセルが整数個の出力ピクセルに対応していないと構造が崩れる。
160x144→640x480 は横4.00倍・縦3.33倍なので、両軸に収まる最大の整数倍は3。

### 測定（指標の訂正を含む）

> **重要：以前このリポジトリの文書に書いた「640x480は行の振れ130%」は過大だった。**
> あの指標（行ごとの輝度の最大/最小）は、*意図した構造の深さ* と
> *セルごとに模様が変わる不良* を区別できていない。
> 正しくは **1セル分の移動平均を取ってから** max/min を見る。
> 構造は平均で消え、うねり（不良）だけが残る。以下はその指標。

| 出力 | 倍率 | 行のうねり | 列のうねり | 平均 R:G:B |
|---|---|---:|---:|---|
| **480x432**（現在の既定） | 3.00 / 3.00 | **4.9%** | **2.6%** | 0.98:1.00:0.93 |
| 576x432（4:3・縦だけ整数） | 3.60 / 3.00 | 5.0% | 11.8% | 0.98:1.00:0.93 |
| 640x480（素朴に全画面） | 4.00 / 3.33 | 18.5% | 2.5% | 0.88:1.00:0.83 |
| **640x480（下記の試作）** | 4.00 / 3.33 | **8.9%** | **2.4%** | **0.98:1.00:0.99** |

つまり 4.9% 対 8.9% の勝負であって、以前示唆したような致命差ではない。
**4:3を採るかどうかは見た目の好みで決めてよい。**

## 4. 640x480ネイティブ版の試作（未コミット。ここに全部残す）

ユーザーの目視確認用に作ったが、コミットしていない。採用する場合はこれを実装する。

### 設計の要点は2つ

**(a) 横は最初から整数4倍なので、R・G・B・黒 の4ピクセルにする。**

3素子を4ピクセルに割ると均等に分けられず、赤が12%・青が17%落ちて色が偏る
（0.88:1.00:0.83）。4番目を黒（セル間の枠）にすると **0.98:1.00:0.99** となり、
480x432版（0.93）より良い。ユーザーが以前要望していた「素子間の黒線」も
これで自然に入る。

```glsl
/* 640幅では1セルがちょうど4出力ピクセル。3素子は4に割り切れないので、
 * 素子を歪めるのではなく4番目をセル間の黒枠に充てる。実機にもそこには枠がある。 */
float sub  = fract(cell.x / gg_subcells);
float idx  = floor(sub * 4.0);                       /* 0,1,2 = R,G,B   3 = 枠 */
float band = (min(idx, 2.0) + 0.5) / 3.0;
vec3  mask = 0.5 + 0.5 * cos(TAU * (band - vec3(1.0, 3.0, 5.0) / 6.0));
vec3  stripe = mix(vec3(1.0), 2.0 * mask, gg_subpixel);
const float QUADGAP = 0.85;
stripe *= (idx > 2.5 ? (1.0 - QUADGAP) : 1.0) / (1.0 - QUADGAP * 0.25);
```

**(b) 縦3.33倍のうねりは、行の断面を出力ピクセルの範囲で積分して減らす。**

点で拾うと、出力ピクセルがセルのどこを切るかが行ごとに変わり、それがうねりになる。
ピクセルの高さぶん積分すれば実際のセンサーと同じ扱いになる。18.5%→12.0%。
4分割で収束し、8分割にしても11.8%で変わらない。

```glsl
/* 行の断面を点で拾わず、出力ピクセルの高さぶん積分する。 */
float ey2 = 0.0;
for (int k = 0; k < 4; k++) {
   float off = (float(k) + 0.5) / 4.0 - 0.5;
   float pk  = fract(cell.y + off * (TextureSize.y / OutputSize.y));
   float e   = abs(pk - 0.5) * 2.0;
   ey2 += e * e;
}
ey2 *= 0.25;
/* grid の ey*ey をこの ey2 で置き換える */
```

さらに `gg_rowgap` を 0.80→**0.60** に落とすと 12.0%→**8.9%**。
このとき横線の濃さは40%で、480x432版の33%と同等になる（強さの釣り合いが取れる）。

| `gg_rowgap` | 行のうねり | 横線の濃さ |
|---|---:|---:|
| 0.80 | 12.0% | 69% |
| **0.60** | **8.9%** | **40%** |
| 0.45 | 7.4% | 27% |

## 5. 色を実機に合わせる手順（再現方法）

`89d076d` でやったこと。同じ手順で他のゲームでも検証できる。

### 材料

1. **実機の画面写真**（今回は故障個体。右2/3が白くなるので**左1/3だけ**使う）
2. **同じ場面のクリーンなスクリーンショット**（480x432。`[1::3, 1::3]` で160x144へ）

今回使ったのは Sonic the Hedgehog 2 のタイトル画面。
ユーザーの `~/Downloads/20260908-020335.png`（実機とシェーダーの並び）と
`~/Downloads/Sonic the Hedgehog 2 (JUE).png`（クリーン）。**移動・削除される可能性あり。**

### 手順

1. 合成画像を左右に割る。今回は境界が x=520 付近の暗い列
2. 写真内の**画面矩形**を求める。行・列ごとの平均輝度でベゼルとの段差を探す。
   今回は右パネルのcrop座標で x 16..517、y 24..400
3. **故障領域の境界**を求める。輝度が段状に上がる列。今回は x≈172（左31%が正常）
4. **位置合わせを目視で確認する。** ソースを画面矩形へ写像し、市松模様に
   交互配置して重ねる。特徴（文字、翼）がずれていないこと。
   **これを飛ばすと測定を信じてしまう。実際、最初は箱の位置がずれていた**
5. ソースの**色ごとにマスク**を作り（`|src - colour| < 8`、1px収縮）、
   写像先の写真の画素を平均する。故障領域は除外
6. 彩度は `(max-min)/mean`、色相は `rgb / max` で比較

### 今回の測定結果（実機）

| ソースの色 | 実機の彩度 | 実機の色相 R:G:B | 実機の輝度 |
|---|---:|---|---:|
| 背景 (0,0,140) | 0.15 | 0.86 / 0.96 / 1.00 | 0.347 |
| 白 (239,239,239) | 0.08 | 0.92 / 1.00 / 0.95 | 0.814 |
| 赤橙 (239,69,0) | 0.60 | 1.00 / 0.67 / 0.55 | 0.594 |
| 水色 (66,69,239) | 0.03 | 1.00 / 1.00 / 0.97 | 0.640 |
| 左1/3の領域平均 | — | 0.944 / 0.999 / 1.000 | 0.372 |

### 落とし穴（重要）

- **絶対輝度を合わせにいかないこと。** 同じソース色が画面内の位置によって
  0.27〜0.45 とばらつく（バックライトむらと故障）。彩度・色相は1枚の画像内の
  比なので耐えるが、輝度は耐えない。
  実際、輝度を目的関数に入れた自動フィットは彩度0.07（ほぼ白黒）に潰れた
- **自動フィットに頼りすぎないこと。** 個体1台・故障品・カメラのホワイトバランス不明。
  ランプの色を自由にすると黄色へ飛んで絵が褐色になる。
  実機の白（0.92/1.00/0.95）で拘束してから振ること
- 階調カーブは数値ではなく**目で決めた値**のままにしてある。上記の理由による

## 7. 触ってはいけないもの（実機で好評だった部分）

- **滲み（`Diffusion across` / `Diffusion down`）。** ユーザーから明示的に
  「いい感じ」と評価された唯一の項目。3x3の9フェッチに畳み込んである
- **素子の位置ずれ（`Element offset`）。** 縁の暖色／寒色フリンジ
