# Game Gear LCDシェーダー 導入・動作確認 引き継ぎ

この文書はGame Gear LCDシェーダーをBubble実機へ導入し、受け入れ確認を行うための
引き継ぎである。シェーダーが何を再現しているか、パラメータの意味は
`docs/gamegear-lcd-shader.md` を参照する。

> **作業を引き継ぐ場合はまず `gamegear-lcd-shader-next-steps.md` を読むこと。**
> 未決事項（アスペクト比の選択）と、実機確認待ちの変更がまとめてある。

## 1. 位置づけ

RetroArchでGame Gearを動かしたときに、汎用のLCDフィルタではなく**実機のパネル**の
見え方を再現する。実機写真を基準に調整してある。

GGFEとは独立している。GGFEを使わずRetroArchを直接起動しても効く。

### ファイル

| パス | 内容 |
|---|---|
| `configs/retroarch/shaders/gamegear-lcd.glslp` | 本体（2パス） |
| `configs/retroarch/shaders/gamegear-lcd-response.glsl` | パス1: パネル応答（残像） |
| `configs/retroarch/shaders/gamegear-lcd-panel.glsl` | パス2: セル構造・色域・バックライト |
| `configs/retroarch/shaders/gamegear-lcd-panel-only.glslp` | 切り分け用（パス2のみ） |
| `scripts/preview-gamegear-lcd.py` | ホスト検証（numpy再実装） |

### なぜGLSLなのか

`scripts/build-bubble-retroarch.sh` が `--enable-opengles --disable-opengl_core` で
構成しているため、**この機体にはglcoreもVulkanも無く、slangは読み込めない**。
GLSL以外の形式を書いても動かない。

## 2. 現状（検証済みと未検証を厳密に分ける）

### 実機で確認済み（2026-09-07）

- panel-only版・FULL版とも読み込めた。**GLSLはコンパイルを通る**
- 過去フレームのuniform名も、明るさの差が報告されていないことから正しいと判断
- 実機フィードバックを受けて調整済み: 明るさ、コントラスト（より白っぽく）、
  RGB素子のサイズ

### ホスト側で検証済み

- RetroArchビルドが通り、4ファイルが `factory-defaults/shaders` へ入りchecksumに載る
- `plumos-retroarch-launch` が `config/shaders` へ**上書きせず**seedする
- `system=gamegear`だけがKMS/EGL/GLESへ切り替わり、2パス版を
  `--set-shader`で読むlauncher contractが通る
- NESなどの非Game Gear経路はplain DRMのままで、同じGenesis Plus GXを使う
  Master System/Mega Driveにも波及しない
- 切り分け用の`panel-only`と緊急回避用の`off`、不正値拒否がhost testを通る
- **見た目**は `scripts/preview-gamegear-lcd.py` によるnumpy再実装で確認済み。
  既定値はこれでスイープして決めた

### 未検証

ツールイメージにglslangValidatorが無いためコンパイル検証はホストでは行えない。
初回の実機確認でロードは通ったが、以下は未確認のまま。

- 調整後の見え方（前回の実機確認は調整前の値）
- フレームレートへの影響
- 残像の効き具合（動きのあるゲームでの確認が必要）

## 3. デプロイ

**retroarchとfrontendの2コンポーネントを同じapp-layer更新単位で入れ替える。**
シェーダー本体はretroarch、Game Gearだけへ限定する起動契約はfrontendが所有する。
checksums/manifestの整合が必要。

```
./scripts/build-bubble-retroarch.sh
./scripts/build-bubble-frontend.sh
./scripts/build-bubble-app-layer.sh --assemble-only
```

永続cfgの`video_shader_enable`は`false`のままにする。Game GearのRetroArch起動時だけ
launch append cfgで有効にし、`gamegear-lcd.glslp`を指定する。これにより他systemは
従来どおりで、ユーザーのRetroArch設定も書き換えない。

GGFEでPicoArch profileを選んだ場合はRetroArchシェーダーを利用できない。
`retroarch:genesis_plus_gx`、`retroarch:picodrive`、`retroarch:gearsystem`のいずれかを
選んだ場合に適用される。

## 4. 動作確認手順

### 4.1 まず切り分け用のパス2だけを読む

いきなり本体を読むと、失敗したときにパス1とパス2のどちらが原因か分からない。

validation holdでFEの停止を確認してから、通常launcherへ
`PLUMOS_GAMEGEAR_LCD_PRESET=panel-only`を渡してGame Gearを起動する。
RetroArchメニューから手動ロードする場合は
`Shaders > Load Preset > gamegear-lcd-panel-only.glslp > Apply`でもよい。

**ここで色味とセル構造が出れば、パス2は正常。** 出なければパス2の問題。

### 4.2 本体を読む

`PLUMOS_GAMEGEAR_LCD_PRESET`を付けない通常FE経路で起動する。既定はfullであり、
`gamegear-lcd.glslp`が自動適用される。切り分け時だけ明示的に`full`を渡してもよい。

シェーダーが起動不能または著しい性能低下を起こす場合に限り、切り分け用として
`PLUMOS_GAMEGEAR_LCD_PRESET=off`を使える。これは永続設定を変更しない。

### 4.3 確認項目

| # | 項目 | 期待 |
|---|---|---|
| 1 | ロード | エラーにならない |
| 2 | 色味 | 全体が青緑に寄り、明るいグレーが淡い青になる |
| 3 | 構造 | 細い横線が見え、その間に色のテクスチャがある |
| 4 | 残像 | 動くものが尾を引く。静止画では尾は出ない |
| 5 | 明るさ | パス2のみ と 本体 で明るさがほぼ同じ |
| 6 | fps | シェーダー有効時も従来どおり |
| 7 | 復帰 | 終了してFEに戻れる |

**5が重要**である。理由は5章。

### 4.4 記録

`docs/validation/YYYY-MM-DD-bubble-gamegear-lcd-shader.md` へ既存形式で残す。
実機写真があると調整に直結するので、可能なら添付する。

## 5. 最も可能性が高い失敗要因

### 過去フレームのuniform名（サイレント失敗しうる）

パス1は過去の入力フレームを以下の名前で受け取る前提で書いてある。

```
PrevTexture, Prev1Texture, Prev2Texture, Prev3Texture
```

RetroArchのGLSL仕様ではこれで正しいはずだが、**確認できていない**。

厄介なのは、**名前が違ってもコンパイルは通る**ことである。バインドされない
samplerは黒を返すため、エラーにはならず「全体が暗くなる」という形で出る。

切り分けは4章の手順で完結する。

- パス2のみ → 正常な明るさ
- 本体 → 明らかに暗い、または動きに対して妙に鈍い

この症状なら過去フレームのバインドを疑う。応急処置としては
`gamegear-lcd-panel-only.glslp` をそのまま使えばよい（残像以外は再現される）。

### 精度

セル位相は「ソースのピクセル番号」から作るので、値が160に達する。
mediumpだと分解能が約1/8しかなく、`fract()` が量子化してストライプが縞になる。
`GL_FRAGMENT_PRECISION_HIGH` があればhighpを要求するようにしてあるが、
Mali側がこれを持たない場合は縞が出る可能性がある。

症状が出た場合は `Subpixel strength` を下げれば緩和する。

## 6. 見え方が違うときのパラメータ

RetroArchのシェーダーパラメータメニューから調整できる。実機を見ながら振るのが早い。

| 症状 | 触るもの |
|---|---|
| 全体が暗い／明るすぎる | `Brightness`（倍率ではなく飽和定数。上げるほど明るく眠くなる） |
| 滲みが強すぎる／足りない | `Diffusion across` / `Diffusion down`（ソースピクセル単位） |
| 縁の色ずれが強すぎる | `Element offset` を下げる |
| セルの黒枠が強すぎる／足りない | `Column gap` |
| RGB素子が見えない | `Element luma balance` を0へ（下記）。次に `Subpixel strength` を上げる |
| 全体が白っぽく眠い | `Black level` を下げ、`Panel gamma` を上げる |
| 青が実機より鮮やかすぎる | `Weak blue filter` を上げる |
| 画面全体の色被り | `Panel cast`（青被りではなく淡い緑。実機の白を測った値） |
| 構造が不規則・画面を流れる | 整数3xで描けていない。下記「整数倍スケーリング」 |
| 眠すぎる／コントラストが強すぎる | `Black level`（下げると締まる） |
| 青被りが強すぎる／足りない | `Blue cast` |
| 横線が目立ちすぎる／見えない | `Row gap` |
| RGB素子が小さい／大きい | `Subpixel size (cells)`。1が実寸、2以上は強調 |
| 色縞がうるさい | `Subpixel strength` を下げる |
| 灰色部分に縦線が出る | 対策済み（下記「縦線について」）。なお残るなら `Column gap` を下げる |
| 残像が長すぎる／足りない | `LCD fall speed`（下げると尾が伸びる） |

調整結果が良ければ、その値を `gamegear-lcd-panel.glsl` の `#pragma parameter`
既定値へ反映してコミットすること。実機で決めた値のほうが正しい。

### 縦線について（対処済み）

灰色部分に縦線が見える、という報告があった（G-LOCの計器パネルなど）。
原因はRGBストライプの**輝度が帯ごとに揃っていなかった**こと。
輝度の内訳は緑が大半で青がほとんど無いため、素の状態では緑帯が青帯より55%明るく、
ストライプが色ではなく明暗の縞として出ていた。灰色は3チャンネルが等しく
他に変化が無いので、この縞だけが残って最も目立つ。
`Subpixel size (cells)` を2にして素子を大きくしたことで周期が6ピクセルになり、
3ピクセル周期のときは目で分離できなかったものが見えるようになった。

対策として、ストライプを自身の輝度で割ってから使うようにした。
帯ごとの違いは色相だけになり（帯内の彩度差は93%のまま、輝度は全帯ちょうど1.0）、
人間の色の解像力は輝度の約1/3しかないので縞として分離されない。
平坦な灰色での列ごとの輝度差は24%→7%になり、残る7%はストライプではなく
セルグリッドの `Column gap` によるもの。

### STN感について（実機写真との突き合わせ）

実機写真と並べたところ、フィルターは「綺麗な格子を綺麗な絵に重ねた」状態で、
実機の眠さが出ていなかった。差の内訳は次の3点で、いちばん効いたのは滲みである。

1. **滲み（最重要）。** 偏光板と前面プラスチックがセルの光を隣へ広げるので、
   実機は輪郭が1ピクセルほど溶け、小さい文字は半分潰れる。
   `Diffusion across` / `Diffusion down` で入れた。横に広く縦に狭いのは、
   横線が実機で最初に目に入る構造であり、縦に同じだけぼかすと消えてしまうため。
2. **素子ごとの位置ずれ。** 赤の帯はセル中心の左、青は右に約1/3セルある。
   これがスプライトや文字の縁の暖色／寒色のフリンジになる。`Element offset`。
3. **セルの黒枠。** `Column gap` を0.35へ。素子が格子として整理され、
   「点が密に散っている」感じが減る。

実装は3x3の9フェッチ1回にまとめてある。位置ずれはサブピクセル単位のずれなので、
チャンネルごとに別の場所を読む（フェッチ3倍）のではなく、同じ9タップに対する
横方向の重みをチャンネルごとに変える形で畳み込んでいる。
ソースは160x144なので9フェッチとも全てキャッシュに載る。
タップが端で1テクセルはみ出すため、プリセットに `wrap_mode = clamp_to_edge` を追加した。

なお `Subpixel size (cells)` を2以上にして素子を大きくする方向は**失敗だった**。
実機の素子ピッチから外れて絵が粗くなるだけで、STN感は出ない。既定を1へ戻してある。

### 平坦な灰色の縦縞について

前回、輝度を揃えて1.7%まで落とした。今回 `Column gap` を0.35にしたことで
12%へ戻っているが、これは**周期が3出力ピクセル**のセル構造そのものであり、
問題だった帯（周期6ピクセル）とは別物である。3ピクセル周期は目が分離できないので
縞には見えない。もし実機で気になるようなら `Column gap` を下げること。

### 4:3非スクエアピクセルとcoverage積分

パネルパスはセル格子とRGBストライプの位相を**ソースピクセルから**取る。
現在は出力1ピクセルの面積内にあるRGB素子と行境界を解析的に積分するため、
非整数倍でも色の偏りと周期的なモアレを抑えられる。

160x144を640x480へ入れると横4.00倍・縦3.33倍となり、実際の4:3開口に対応する
横長のドットになる。既定はこの **640x480 `sega43`**。
旧 **480x432** は `PLUMOS_GAMEGEAR_LCD_GEOMETRY=integer3x` で比較用に残す。
RetroArchの `custom_viewport_x/y` は画面上の絶対座標ではなく、viewport biasで決まる
中央位置への追加オフセットである。既定bias 0.5では `x=0, y=0` が物理座標80,24となる。
ここへ80,24を指定すると中央寄せが二重適用され、実機では右下へずれる。

従来は `aspect_ratio_index = "22"`（コア指定）＋ `video_scale_integer = "false"` で
RetroArch任せだったため、非整数倍で描かれていた。平坦な灰色での実測：

| 出力 | 倍率 | 列の振れ | 行の振れ | 平均 R:G:B |
|---|---|---:|---:|---|
| 640x480 | 横4.00 縦3.33 | 21% | 128% | 0.82 : 1.00 : 0.95 |
| 576x432 | 横3.60 縦3.00 | 38% | 34% | 0.92 : 1.00 : 1.05 |
| 533x480 | 横3.33 縦3.33 | 53% | 139% | 0.92 : 1.00 : 1.04 |
| **480x432** | **横3.00 縦3.00** | **15%** | **33%** | 0.92 : 1.00 : 1.05 |

整数3x以外では行間が出力グリッドと干渉して振れが4倍以上になり、画面を上下に流れる。
640x480では3素子を4ピクセルに割り当てることになり均等に分けられないので、
赤が18%落ちて画面全体が色被りする。

正方ピクセル＋整数倍ではなくカスタムビューポートにしたのは、この機種のパネルが
640x480固定であり、コアが申告するアスペクト比やRetroArch側の丸め方に依存しない
確実さを優先したため。他機種へ移植する場合はこの数値をそのまま使わず、
その表示解像度での最大整数倍を計算し直すこと。

黒帯が出るのが嫌で全画面に伸ばしたくなるが、**それをするとこのシェーダーは破綻する**。

### 素子が見えない件と「白っぽい」件（実機で判明・対処済み）

実機写真から2点。**素子が全く見えない**のと、**全体が白っぽい**。

**素子が見えない原因は、前回入れた輝度均一化そのものだった。**
ストライプの3帯は輝度が揃っておらず（緑が明るく青が暗い、約55%差）、
これを割って均すと帯の違いは色相だけになる。色の解像力は輝度の約1/3しかないので、
素子ピッチ（3出力ピクセル）では**目に見えなくなる**。実測でも、均一化しても
帯ごとの色差は0.343→0.345とほぼ不変なのに、明るさの振れは0.230→0.100と半分以下になる。
つまり素子を見せていたのは色ではなく明るさの差だった。

均一化は素子を2セル幅にしていた頃（周期6ピクセル）の対策であり、
あの時点では正しかった。物理ピッチに戻した今は周期3ピクセルで、
これは目が線として分離できない領域なので均す必要がない。
`Element luma balance` として残し、**既定を0**とした。
`Subpixel size (cells)` を2以上に上げるときだけ、これも一緒に上げること。

**白っぽい件は階調の割り当て。** 黒が0.40・白が0.79で、画面全体が
レンジの39%、しかも全部上半分に押し込まれていた。
`Black level` 0.28→0.14、`Panel gamma` 0.90→1.35、`Brightness` 2.30→2.60 とし、
黒0.26・白0.81でレンジの56%を使うようにした。
STNなので眠いのは正しいが、上端に潰れているのは別問題だった。

### 色を実機に合わせた件（Sonic 2のタイトル画面で測定）

実機写真とソースのスクリーンショットを色ごとに対応させて測ったところ、
実機は単に彩度が低いのではなく**選択的**だった。

| ソースの色 | 実機の彩度 | 修正前のシェーダー |
|---|---:|---:|
| 背景（ROM上は純青） | 0.15 | 0.86 |
| 文字の水色 | 0.03 | 0.60 |
| 帯の赤 | 0.60 | 0.45 |

青はほぼ無彩色で届くのに、赤はシェーダーより**濃い**。
全体の彩度では再現できない（背景を灰色にすると帯まで灰色になる）。
同じ領域の平均色相も実機 R:G:B 0.944/0.999/1.000 に対し修正前は 0.635/0.683/1.000。

そこで `Weak blue filter` で青だけを洗う。モデルを2つ測って片方だけが合った。

- **光を足す**（漏れやすいフィルタとして）→ 背景の彩度を0.15に合わせると
  背景が白の1.5倍以内まで持ち上がる。実機では「PRESS START BUTTON」が
  背景に対してはっきり読める。**不採用**。
- **輝度を戻しつつ色だけ落とす** → 彩度0.16（実測0.15）、明るさ0.32（0.35）、
  白/背景コントラスト2.6（2.4）。**採用**。

ランプの色も仮定ではなく測った。実機の白は R:G:B 0.92/1.00/0.95 の**淡い緑**。
従来は青被りにしていたがこれは逆方向で、青が強すぎた一因。
パラメータ名も `Blue cast` → `Panel cast` に変更。

**注意点。** 個体は1台、しかも右2/3が白くなる故障品なので左1/3のみを標本にした。
カメラのホワイトバランスも不明。彩度の話は1枚の画像内の比なのでこれらに耐えるが、
絶対輝度は耐えない（同じソース色が画面内で0.27〜0.45とばらつく）。
よって階調カーブは数値に合わせず、目で決めた値のままにしてある。

## 7. 仕様であって不具合ではない挙動

- **高速で動くものが最大輝度に届かない。** STNパネルの実際の挙動である。
- **サブピクセルは3x前提で位相を合わせてある。** 整数3x以外に拡大された場合は
  位相が合わず色縞になる。その場合は `Subpixel strength` を下げる。
- **文字が読みにくい。** 実機がそうである。滲みを弱めたい場合は
  `Diffusion across` を下げる。
- **静止画では残像が出ない。** 履歴と現在値が一致するため、パス1は素通しになる。

## 8. 自動適用の境界

既定でGame Gearへ適用するが、`video_shader_enable = true`を出荷cfgへは入れない。
system idを見られる`plumos-retroarch-launch`が起動単位で適用する。

コア別プリセットとして保存してはならない。Genesis Plus GXやPicoDriveはGame Gear以外も
実行するため、Master System、Mega Drive、Sega CDへ誤適用される。
